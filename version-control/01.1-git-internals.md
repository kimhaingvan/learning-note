## 1. Core Mental Model

The two most important things to understand about Git:

> **Git does NOT store history as "a list of changed lines".**
> **Git stores snapshots of the entire project state as immutable objects, identified by hash.**

Git works like a **content-addressable filesystem**:

```
Content determines the storage address.
```

---

## 2. Three Data Areas

When working with Git, you interact with three areas:

```
Working Directory
      │
      │  git add
      ▼
Staging Area / Index
      │
      │  git commit
      ▼
Repository / Object Database (.git/)
```

**Working Directory**

The files you see and edit:
```
project/
├── index.html
├── app.js
└── README.md
```

The working directory may not match the most recent commit.

**Staging Area**

Also called the **index**. It stores the state you want to put into the next commit.

When you run:
```bash
git add README.md
```

Git does not just "mark the file". It:
1. Reads the file content.
2. Creates a blob object.
3. Saves the blob into the object database.
4. Updates the index to point to that blob.

**Repository**

The `.git/` directory. It contains:
- Object database
- Commits
- Branches
- Tags
- Index
- Reflog
- Remote config
- Repository configuration

---

## 3. The `.git` Directory

Running `git init` creates:

```
.git/
├── HEAD
├── config
├── description
├── index
├── objects/
├── refs/
├── logs/
├── hooks/
├── info/
└── packed-refs
```

| Component | Purpose |
|-----------|---------|
| `.git/objects/` | Where all Git objects are stored |
| `.git/refs/` | Stores branches and tags |
| `.git/HEAD` | Tells Git which branch or commit you are currently on |
| `.git/index` | Staging area |
| `.git/config` | Repository configuration |
| `.git/logs/` | Reflog |
| `.git/hooks/` | Scripts that run on Git events |
| `.git/packed-refs` | Compacted refs |

---

## 4. Four Core Object Types

Git has exactly four object types:

| Object | Stores |
|--------|--------|
| **blob** | File content only |
| **tree** | Filenames, modes, blob/tree references |
| **commit** | Snapshot metadata + pointer to root tree + parent(s) |
| **tag** | Pointer to an object + tagger + message |

Relationship:
```
commit
  │
  ├── tree
  │    ├── blob
  │    ├── blob
  │    └── tree
  │         └── blob
  │
  └── parent commit
```

---

## 5. Blob Object

A blob stores **only file content**.

A blob does **not** store:
- Filename
- File path
- Last modified time
- Owner

```bash
# Hash a file without saving
echo "Hello Git" | git hash-object --stdin
# → 557db03de997c86a4a028e1ebd3a1ceb225be238

# Hash and save into the object database
echo "Hello Git" | git hash-object -w --stdin
```

The object is now stored at:
```
.git/objects/55/7db03de997c86a4a028e1ebd3a1ceb225be238
```

Git splits the hash: the first 2 characters become the directory name, the rest become the filename.

---

## 6. Why Identical Files Are Not Stored Twice

Suppose:
```
a.txt = "Hello Git"
b.txt = "Hello Git"
```

Both files have the same content → Git produces the same blob hash:

```
a.txt ─┐
       ├── blob 557db03...
b.txt ─┘
```

Git stores the blob **once**. Filenames are stored in the **tree** object, not in the blob. This is natural **deduplication**.

---

## 7. How the Hash Is Computed

Git does not hash raw file content directly. For a blob, Git builds:

```
blob <size>\0<content>
```

Example for `"Hello Git\n"` (10 bytes):
```
blob 10\0Hello Git\n
```

Then Git computes:
```
SHA-1("blob 10\0Hello Git\n")
```

> Some modern repositories use SHA-256, but SHA-1 is still the default.

The object ID depends on:
- Object type
- Content size
- Content

**One character change → completely different hash.**

## Kiểm tra một file đang trỏ đến blob nào

Để xem một file trong Git đang được lưu dưới blob object nào, sử dụng:

```bash
git ls-files --stage <file-path>
```

Ví dụ:

```bash
git ls-files --stage README.md
```

Kết quả:

```text
100644 e69de29bb2d1d6434b8b29ae775ad8c2e48c5391 0 README.md
```

Ý nghĩa các trường:

| Trường | Ý nghĩa |
|--------|---------|
| `100644` | File mode |
| `e69de29bb2d1d6434b8b29ae775ad8c2e48c5391` | Blob SHA-1 |
| `0` | Stage (index) |
| `README.md` | Tên file |

Blob object sẽ được lưu tại:

```text
.git/objects/e6/9de29bb2d1d6434b8b29ae775ad8c2e48c5391
```

> Git chia SHA thành:
>
> - Thư mục: 2 ký tự đầu (`e6`)
> - Tên file: 38 ký tự còn lại (`9de29bb2d1d6434b8b29ae775ad8c2e48c5391`)

# Đọc nội dung từ blob object

Blob file trong `.git/objects` **không chứa trực tiếp nội dung file**, mà được Git nén bằng **zlib**.

Cách đơn giản nhất để đọc nội dung blob:

```bash
git cat-file -p <blob-sha>
```

Ví dụ:

```bash
git cat-file -p e69de29bb2d1d6434b8b29ae775ad8c2e48c5391
```

Git sẽ tự:

1. Tìm blob object.
2. Giải nén dữ liệu.
3. Bỏ phần header của blob.
4. Hiển thị nội dung file dưới dạng có thể đọc được.

---

# Cấu trúc của một Blob Object

Sau khi giải nén, dữ liệu blob có cấu trúc:

```text
blob <size>\0<file-content>
```

Ví dụ:

```text
blob 12\0Hello World
```

Trong đó:

- `blob`: Loại object.
- `<size>`: Kích thước nội dung file (byte).
- `\0`: Ký tự null (`0x00`) phân tách header và nội dung.
- `<file-content>`: Nội dung thực tế của file.

Ví dụ dưới dạng byte:

```text
62 6c 6f 62 20 31 32 00 48 65 6c 6c 6f 20 57 6f 72 6c 64
```

Trong đó:

- `62 6c 6f 62` → `"blob"`
- `20` → dấu cách
- `31 32` → `"12"`
- `00` → ký tự null (`\0`)
- Phần còn lại → nội dung file (`Hello World`)

> Git tính SHA-1 của blob dựa trên toàn bộ chuỗi:
>
> ```text
> blob <size>\0<file-content>
> ```
>
> Vì vậy, chỉ cần thay đổi một byte trong header hoặc nội dung thì SHA của blob cũng sẽ thay đổi.

---

# Blob Versions của một File

Một file trong Git **không chỉ có một blob duy nhất**. Mỗi khi nội dung file thay đổi và được commit, Git sẽ tạo **một blob mới**.

Ví dụ:

```
Commit A
README.md
└── Blob A (SHA: a1b2c3)

Commit B
README.md
└── Blob B (SHA: d4e5f6)

Commit C
README.md
└── Blob C (SHA: 789abc)
```

Mặc dù đều là `README.md`, nhưng mỗi phiên bản nội dung sẽ có một blob khác nhau.

# Minh họa

Giả sử:

**Commit A**

```text
Hello
```

Blob được tạo:

```
Blob A
↓
blob 5\0Hello
```

---

**Commit B**

```text
Hello World
```

Blob mới:

```
Blob B
↓
blob 11\0Hello World
```

Blob A vẫn được giữ nguyên trong database của Git.

---

**Commit C**

```text
Hello World!!
```

Git tiếp tục tạo:

```
Blob C
↓
blob 13\0Hello World!!
```

Kết quả:

```
Repository

Commit A
   │
   └──── README.md ───► Blob A

Commit B
   │
   └──── README.md ───► Blob B

Commit C
   │
   └──── README.md ───► Blob C
```

---

# Blob là immutable

Blob object trong Git là **immutable** (không thể sửa).

Khi nội dung file thay đổi:

- ❌ Git **không cập nhật blob cũ**.
- ✅ Git **tạo blob mới**.
- Commit mới sẽ trỏ đến blob mới.

Nhờ vậy, Git luôn lưu được toàn bộ lịch sử của file.

---

# Git chỉ lưu blob khi nội dung thay đổi

Nếu file **không thay đổi nội dung** giữa hai commit, Git sẽ **không tạo blob mới**.

Ví dụ:

```
Commit A
README.md
└── Blob X

Commit B (không sửa README.md)
README.md
└── Blob X

Commit C (vẫn không sửa README.md)
README.md
└── Blob X
```

Ba commit cùng tham chiếu đến **một blob duy nhất**.

```
            Blob X
           /   |   \
          /    |    \
   Commit A  Commit B  Commit C
```

Đây là một trong những lý do Git tiết kiệm dung lượng lưu trữ: **blob được chia sẻ giữa nhiều commit nếu nội dung hoàn toàn giống nhau**. Chỉ khi nội dung thay đổi, Git mới sinh ra blob mới với một SHA khác.

## 8. Objects Are Immutable

A Git object, once created, is **never modified**.

```
Version 1 → blob abc123
Version 2 → blob def456
```

`blob abc123` still exists. When a file changes, Git creates a **new object**.

---

## 9. Tree Object

A tree object is like a directory. It stores:
- Filenames
- Modes
- Blob IDs (for files)
- Tree IDs (for subdirectories)

Example project:
```
project/
├── README.md
├── app.js
└── src/
    └── main.js
```

Git stores it as:
```
root tree
├── README.md → blob A
├── app.js    → blob B
└── src       → tree C
                   └── main.js → blob D
```

```bash
git ls-tree HEAD
# 100644 blob a1b2c3...    README.md
# 100644 blob d4e5f6...    app.js
# 040000 tree 123abc...    src
```

**File modes:**

| Mode | Meaning |
|------|---------|
| `100644` | Regular file |
| `100755` | Executable file |
| `040000` | Directory / subtree |
| `120000` | Symbolic link |
| `160000` | Git submodule |

> Git does not store full Unix permissions. It mainly cares about whether a file is executable or not.

---

## 10. Commit Object

A commit object stores the **metadata of a snapshot**:

```
tree      <tree-hash>
parent    <parent-commit-hash>
author    <name> <email> <timestamp>
committer <name> <email> <timestamp>

commit message
```

Example:
```
tree 9c1a...
parent 8b2f...
author Kim Hai <email@example.com> 1784019600 +0700
committer Kim Hai <email@example.com> 1784019600 +0700

Add homepage
```

```bash
git cat-file -p HEAD
# tree 630f...
# parent a7bc...
# author Kim Hai <kimhai@example.com> 1784019600 +0700
# committer Kim Hai <kimhai@example.com> 1784019600 +0700
#
# Add homepage
```

**A commit does not contain files directly.** It points to the root tree → which points to blobs and subtrees → representing the complete project snapshot.

```
commit
  └── root tree
       ├── blob
       ├── blob
       └── subtree
            └── blob
```

---

## 11. Parent Commits Form History

A normal commit has one parent:
```
A ← B ← C
```

Commit C contains `parent B`. Commit B contains `parent A`. The first commit has no parent.

A merge commit has two parents:
```
A ← B ← D
     \  /
      C
```

Commit D contains:
```
parent B
parent C
```

Git history is therefore a **Directed Acyclic Graph (DAG)**, not a simple list.

---

## 12. Snapshots Do Not Copy the Entire Project

First commit:
```
README.md → blob A
app.js    → blob B
```

Next commit — only `app.js` changed:
```
README.md → blob A   ← reused
app.js    → blob C   ← new blob only
```

```
Commit 1
└── Tree 1
    ├── README.md → Blob A
    └── app.js    → Blob B

Commit 2
└── Tree 2
    ├── README.md → Blob A   ← reused
    └── app.js    → Blob C   ← new
```

Git creates a new tree (because its content changed) but does **not** create new blobs for unchanged files.

---

## 13. What a Branch Really Is

A branch is just a **small file containing a commit hash**:

```bash
cat .git/refs/heads/main
# 4e6a87445...

git rev-parse main
# 4e6a87445...
```

Branch `main` is stored at `.git/refs/heads/main`.

Branches do **not** contain code. They are **pointers to commits**.

```
main
  │
  ▼
Commit C
  │
  ▼
Commit B
  │
  ▼
Commit A
```

---

## 14. What HEAD Is

`HEAD` tells Git where you currently are.

```bash
cat .git/HEAD
# ref: refs/heads/main
```

Normally: `HEAD → main → commit`

When you make a new commit:

Before:
```
HEAD → main → C
```

After `git commit`:
```
HEAD → main → D
                ↓
                C
```

Git creates commit D, then updates `main` from C to D.

---

## 15. Detached HEAD

Checking out a commit directly:
```bash
git switch --detach abc123
```

`.git/HEAD` now contains the commit hash directly:
```
abc123...
```

Instead of pointing through a branch:
```
HEAD → commit    (not HEAD → branch → commit)
```

If you make commits in this state, those commits do **not automatically belong to any branch**.

---

## 16. Tag Object

Two types of tags:

**Lightweight tag** — just a ref pointing to a commit:
```bash
git tag v1.0
```

**Annotated tag** — a full tag object:
```bash
git tag -a v1.0 -m "Release version 1.0"
```

An annotated tag object stores:
- The object being tagged
- Object type
- Tag name
- Tagger identity
- Message
- Optional GPG signature

```
annotated tag v1.0
      │
      ▼
commit A
```

---

## 17. What the Staging Area Stores

The staging area lives at `.git/index` — a binary file.

It stores entries like:
```
path | file mode | blob hash | metadata | merge stage
```

Example:
```
README.md → blob A
app.js    → blob B
```

When you run `git add app.js`, Git:
1. Reads the content of `app.js`.
2. Creates a new blob.
3. Saves the blob in `.git/objects/`.
4. Updates the `app.js` entry in the index.

```bash
git ls-files --stage
# 100644 a1b2c3... 0    README.md
# 100644 d4e5f6... 0    app.js
```

---

## 18. Why You Can Stage Part of a File

```bash
git add -p
```

This stages individual hunks. The working directory, index, and HEAD can all hold **different versions** of the same file:

```
HEAD version:           line A
Index version:          line A + line B
Working directory:      line A + line B + line C
```

If you commit now, the commit contains only `line A + line B`. Line C has not been staged and is not committed.

---

## 19. What `git commit` Really Does

```bash
git commit -m "Update app"
```

Git:
1. Reads the index.
2. Creates a **tree object** from the index.
3. Takes the current commit as parent.
4. Creates a **commit object**.
5. Updates the current branch ref to point to the new commit.
6. Updates the reflog.

```
Index
  │
  ▼
Tree object
  │
  ▼
Commit object
  │
  ▼
refs/heads/main updated
```

> `git commit` reads the **index**, not the working directory. Unstaged changes are not included.

---

## 20. What `git status` Compares

`git status` performs two comparisons:

| Comparison | Shows |
|------------|-------|
| `HEAD ↔ Index` | "Changes to be committed" (staged) |
| `Index ↔ Working Directory` | "Changes not staged for commit" (unstaged) |

Example:
```
HEAD:    A
Index:   B
Working: C
```

Git reports simultaneously:
- Staged changes: `A → B`
- Unstaged changes: `B → C`

---

## 21. What `git diff` Compares

| Command | Compares | Shows |
|---------|----------|-------|
| `git diff` | Index ↔ Working Directory | Unstaged changes |
| `git diff --staged` | HEAD ↔ Index | What will be committed |
| `git diff HEAD` | HEAD ↔ Working Directory | All changes (staged + unstaged) |

## 22. How Objects Are Stored Physically

Loose objects live in:
```
.git/objects/xx/yyyyyyyy...
```

The process:
1. Build the header + content: `blob <size>\0<content>`
2. Compute the hash.
3. Compress with **zlib**.
4. Save to `.git/objects/`.

Example:
```
blob 10\0Hello Git
        │
        ▼
   zlib compress
        │
        ▼
.git/objects/55/7db03...
```

> Git objects are **not stored as plain text**. Opening them with `cat` shows compressed binary data. Use `git cat-file -p <hash>` instead.

---

## 23. Packfiles

If every object were a separate file, a large repository would contain millions of tiny files. Git solves this with **packfiles**:

```
.git/objects/pack/
├── pack-abc123.pack    ← multiple objects compressed together
└── pack-abc123.idx     ← index for fast object lookup
```

| File | Purpose |
|------|---------|
| `.pack` | Contains many packed and compressed objects |
| `.idx` | Index that lets Git locate objects quickly inside the pack |

Packfiles are created during:
- `git clone`
- `git fetch`
- `git push`
- `git gc`
- `git repack`

---

## 24. Delta Compression

Loose objects generally store full content. Inside packfiles, Git can use **delta compression**.

If two large blobs are nearly identical:
```
Blob A: 10 MB
Blob B: 10 MB, differs by only a few lines
```

Git can store:
```
Blob A: full content
Blob B: delta relative to Blob A
  → "copy section 1 from A, insert X, copy section 2 from A"
```

> **Important**: Delta compression is a **physical storage optimization** inside packfiles. Logically, every blob is still an independent object with its own hash.

---

## 25. Does Git Store Diffs?

At the **logical level**: **No** — Git stores snapshots.

At the **physical storage level**: Git **may use delta compression** in packfiles.

Both of the following statements can be true in different contexts:
- "Git stores snapshots."
- "Git uses deltas to save disk space."

---

## 26. References

Refs are human-readable names pointing to object hashes:

```
refs/heads/main
refs/heads/develop
refs/tags/v1.0
refs/remotes/origin/main
```

| Ref type | Path |
|----------|------|
| Local branch | `refs/heads/main` |
| Remote-tracking branch | `refs/remotes/origin/main` |
| Tag | `refs/tags/v1.0` |

```bash
git show-ref
```

---

## 27. Remote-Tracking Branches

When you run:
```bash
git fetch origin
```

Git downloads objects and updates:
```
refs/remotes/origin/main
```

`origin/main` is **not** a real branch on the server. It is a **local ref** that records:

> The last time you fetched, `main` on remote `origin` was at this commit.

```
Remote GitHub main
      ↓ git fetch
Local origin/main
```

---

## 28. What `origin` Is

`origin` is just a **name for a remote**. It is stored in `.git/config`:

```ini
[remote "origin"]
    url = git@github.com:user/repo.git
    fetch = +refs/heads/*:refs/remotes/origin/*
```

```bash
git remote -v
```

`origin` is not a reserved keyword. You can use any name:
```bash
git remote add github git@github.com:user/repo.git
```

---

## 29. What `git clone` Does

```bash
git clone git@github.com:user/repo.git
```

Git:
1. Creates a new directory.
2. Creates `.git/`.
3. Connects to the remote.
4. Downloads refs.
5. Downloads all necessary objects.
6. Saves objects as a packfile.
7. Creates remote-tracking refs.
8. Creates the local branch.
9. Checks out the snapshot into the working directory.

```
Remote objects
      ↓
.git/objects/pack/*.pack
      ↓
refs/remotes/origin/main
      ↓
refs/heads/main
      ↓
Working directory
```

---

## 30. git fetch

```bash
git fetch
```

- Downloads new objects.
- Updates remote-tracking refs.
- Does **not** modify the working directory.
- Does **not** merge into the local branch.

```
Remote
  ↓ objects
Local object database
  ↓
origin/main updated

Local main stays unchanged
```

---

## 31. git pull

```bash
git pull
```

Roughly equivalent to:
```bash
git fetch
git merge
```

Or if configured for rebase:
```bash
git fetch
git rebase
```

`git pull` is not a distinct storage type — it is a combined operation.

---

## 32. git push

When pushing, Git:
1. Identifies the local ref and the remote ref.
2. Finds objects the remote does not have.
3. Packages them into a packfile.
4. Sends the packfile.
5. Asks the remote to update its ref.
6. Remote validates (fast-forward or policy).
7. Remote updates the branch if valid.

Example:
```
Local main  → Commit D
Remote main → Commit B
```

Git sends:
- Commit C
- Commit D
- Related trees and blobs

Objects the remote already has (A, B) are **not** resent.

---

## 33. Reflog

A branch ref only stores the **current** commit. Reflog records the **history of every position a ref has ever been**:

```bash
git reflog
# d4e5f6 HEAD@{0}: commit: Add login
# a1b2c3 HEAD@{1}: reset: moving to HEAD~1
# 98ab76 HEAD@{2}: commit: Update UI
```

Stored in:
```
.git/logs/HEAD
.git/logs/refs/heads/main
```

Reflog helps recover commits after:
- `git reset`
- `git rebase`
- `git commit --amend`
- Deleting a branch
- Checking out the wrong commit

Example recovery:
```bash
git reset --hard HEAD~1
# Commit appears "lost", but it's still in reflog

git reflog
# abc123 HEAD@{1}: commit: The lost commit

git switch -c recovery abc123
```

---

## 34. Reachable and Unreachable Objects

An object is **reachable** if there is a path from any ref to it:

```
main → commit C → commit B → commit A
```

A, B, and C are all reachable.

After `git reset --hard HEAD~1`:
```
main → commit B → commit A
```

Commit C is no longer reachable **from main**, but it may still be:
- In the reflog
- Referenced by a tag
- Referenced by another branch
- Physically present in the object database

Git does **not** delete objects immediately.

---

## 35. Garbage Collection

```bash
git gc
```

`git gc` can:
- Repack loose objects into packfiles.
- Compress refs.
- Remove objects no longer needed.
- Optimize the repository.
- Process expired reflog entries.

Git often runs maintenance automatically when needed.

Related commands:
```bash
git gc
git repack
git prune
git maintenance
```

> Do not run `git prune` directly unless you fully understand it — it can permanently delete unreachable objects.

---

## 36. Can a Commit Hash Change?

A commit hash depends on:
- Tree hash
- Parent hash
- Author
- Committer
- Timestamp
- Message

If **any** of these change, the commit hash changes.

Example:
```bash
git commit --amend
```

Even if you only change the message, Git creates a **new commit object**:
```
Old commit: A
New commit: B
```

A and B are two separate objects.

---

## 37. Why Rebase Changes Hashes

Rebase creates new commits with a new parent.

Before:
```
A ← B ← C
 \
  D ← E
```

After rebasing C onto E:
```
A ← D ← E ← B' ← C'
```

`B'` has:
- Nearly the same changes as B
- A different parent
- A different committer timestamp

Therefore the hash is different. `C'` must also change because its parent shifted from B to B'.

---

## 38. Merge vs Rebase — Data Perspective

**Merge** — creates a merge commit:

```
A ← B ← M
 \     /
  C ← D
```

M has two parents. The original history is **preserved**.

**Rebase** — creates new commits:

```
A ← C ← D ← B'
```

`B'` is a new commit. History is **rewritten**.

---

## 39. git reset — What Data Changes

`git reset` moves a ref and optionally updates the index and/or working directory.

| Mode | Branch ref | Index | Working Directory |
|------|-----------|-------|-------------------|
| `--soft` | ✅ Changed | ❌ Unchanged | ❌ Unchanged |
| `--mixed` (default) | ✅ Changed | ✅ Changed | ❌ Unchanged |
| `--hard` | ✅ Changed | ✅ Changed | ✅ Changed |

```bash
git reset --soft HEAD~1    # undo commit, keep changes staged
git reset HEAD~1           # undo commit, unstage changes
git reset --hard HEAD~1    # undo commit, discard all changes
```

---

## 40. git restore

Restores data from a source into the index or working directory.

**Restore working directory from index:**
```bash
git restore file.txt
# Index → Working Directory
```

**Restore index from HEAD:**
```bash
git restore --staged file.txt
# HEAD → Index
```

**Restore from a specific commit:**
```bash
git restore --source=abc123 file.txt
# Commit abc123 → Working Directory
```

---

## 41. How Git Stores Renames

Git does **not** store a rename event. It stores before and after snapshots.

Before:
```
old.txt → blob A
```

After:
```
new.txt → blob A
```

When displaying a diff, Git **infers** the rename based on content similarity:

```bash
git diff --find-renames
```

> Rename detection is an **analysis process**, not data fixed in the commit.

---

## 42. How Git Stores Deletions

Git does **not** create a "delete object". The new commit simply has a tree that **omits** the entry.

Before:
```
tree
├── a.txt
└── b.txt
```

After deleting `b.txt`:
```
tree
└── a.txt
```

The blob for `b.txt` still exists as long as an older commit referencing it is reachable.

---

## 43. Empty Directories

**Git cannot store empty directories.**

Git stores files and builds trees from files. A directory with no files has no entries → no tree to store.

The conventional workaround:
```
.gitkeep
```

`.gitkeep` is **not** a Git feature — it is just a regular file to make the directory non-empty.

---

## 44. .gitignore

`.gitignore` is a regular text file that can be committed. It only affects **untracked** files.

It does **not** automatically stop tracking files that are already tracked.

Example — if `.env` was already committed:
```bash
# Adding .env to .gitignore will NOT stop Git from tracking it
git rm --cached .env    # stop tracking without deleting from disk
```

---

## 45. Symbolic Links

Git stores a symlink as:
- Mode `120000`
- A blob containing the **target path** as text

Example:
```
current → releases/v1
```

The blob content:
```
releases/v1
```

Git stores the path string, **not** the content of the file the symlink points to.

---

## 46. Submodules

Submodules are stored in the parent tree with mode `160000`. The entry points to a **commit hash** of the submodule repository.

The parent repository does **not** store the submodule's full file content in its own object database. It stores:
```
submodule path → commit hash
```

Configuration is in `.gitmodules`:
```ini
[submodule "libs/mylib"]
    path = libs/mylib
    url  = git@github.com:user/mylib.git
```

---

## 47. Object Integrity

Since an object's ID is derived from its content, Git can detect corruption.

```bash
git fsck
```

If the content of an object is modified but its filename (hash) is unchanged, recomputing the hash will not match. This gives Git **strong data integrity**.

---

## 48. Object Traversal

To check out a commit, Git follows this chain:

```
commit hash
    ↓
commit object
    ↓
root tree
    ↓
subtrees and blobs
    ↓
create files in working directory
```

To walk history:
```
commit
  ↓ parent
commit
  ↓ parent
commit
  ...
```

```bash
# Create repository
mkdir demo-git
cd demo-git
git init

# Create a file
echo "Hello Git" > README.md
```

State at this point:
```
Working Directory:  README.md (new, untracked)
Index:              empty
Repository:         no commits yet
```

```bash
# Stage the file
git add README.md
```

Git creates a blob and updates the index:
```bash
git hash-object README.md

git ls-files --stage
# 100644 8ab686... 0    README.md
```

```bash

git commit -m "Initial commit"

# Inspect the commit
git cat-file -p HEAD
# tree abc123...
# author ...
# Initial commit

# Inspect the tree
git cat-file -p HEAD^{tree}
# 100644 blob 8ab686...    README.md

# Inspect the blob
git show HEAD:README.md
# Hello Git

# List all loose objects
find .git/objects -type f
```

## 51. How to Read a Blob Object

Git objects are **not stored as plain text**. Each object is:
1. Prefixed with a header: `blob <size>\0`
2. Compressed with **zlib**
3. Saved to `.git/objects/...`

Running `cat .git/objects/a1/b2c3...` shows garbled binary because the data is zlib-compressed.

### Method 1 — Use Git (Recommended)

```bash
# Step 1: find the blob hash
git ls-tree HEAD
# 100644 blob a1b2c3d4e5f678901234567890abcdef12345678    README.md

# Step 2: read the content
git cat-file -p a1b2c3d4e5f678901234567890abcdef12345678
# # My Project
# Hello Git!
```

### Method 2 — Check any object

```bash
git cat-file -t <hash>   # check type  → blob / tree / commit / tag
git cat-file -s <hash>   # check size
git cat-file -p <hash>   # read content
```

### Method 3 — Decompress manually with Python

```python
import zlib

with open(".git/objects/a1/b2c3d4e5...", "rb") as f:
    data = zlib.decompress(f.read())

print(data)
# b'blob 23\x00Hello Git\nThis is README'

# Split header from content
header, content = data.split(b'\x00', 1)
print(header.decode())   # blob 23
print(content.decode())  # Hello Git\nThis is README
```

### Method 4 — One-liner (Linux/macOS)

```bash
python3 - <<EOF
import zlib
print(zlib.decompress(open(".git/objects/a1/b2c3...", "rb").read()))
EOF
```

### Physical structure of a blob

If `README.md` contains `Hello Git` (10 bytes including newline):

```
Raw data before compression:
blob 10\0Hello Git\n

Process:
blob 10\0Hello Git\n
        │
        ▼
   SHA-1 hash → object ID
        │
        ▼
   zlib compress
        │
        ▼
.git/objects/xx/yyyyyyyy...
```

## 52. Overall Mental Model

```
Working Directory
    │
    │ git add
    ▼
Index / Staging Area
    │
    │ git commit
    ▼
Tree object
    │
    ▼
Commit object
    │
    ▼
Branch ref
    │
    ▼
HEAD
```

Inside the object database:
```
Commit
├── Parent commit
├── Metadata (author, committer, timestamp)
├── Message
└── Root tree
    ├── filename → Blob
    ├── filename → Blob
    └── directory → Tree
                     └── filename → Blob
```

Physical layout:
```
.git/objects/
├── loose objects (xx/yyyy...)
└── pack/
    ├── *.pack
    └── *.idx
```

### Six Core Ideas of Git

| Concept | Meaning |
|---------|---------|
| **Snapshot** | Each commit represents the full project state at that moment |
| **Content-addressable** | Objects are identified by a hash of their content |
| **Immutable objects** | Existing objects are never modified; changes produce new objects |
| **Object graph** | Commits, trees, and blobs form a DAG |
| **Refs are pointers** | Branches and tags just point to objects |
| **Packfile & delta compression** | Physical storage optimization — does not change the logical model |

### Quick Reference

```
Blob   = file content
Tree   = filenames + directory structure
Commit = snapshot + metadata + parent(s)
Branch = pointer to a commit
HEAD   = current position
Index  = snapshot being prepared for the next commit
```

### The Whole Picture

```
HEAD
 ↓
main
 ↓
Commit C ──→ Tree C ──→ Blobs
 ↓
Commit B ──→ Tree B ──→ Blobs (some shared with C)
 ↓
Commit A ──→ Tree A ──→ Blobs
```
